# Задание агенту: создать OSS-репозиторий и начать разработку

Версия задания: 1.0. Дата: 15 октября 2026 года.

Ты работаешь как ведущий разработчик нового self-hosted приложения для совершеннолетних участников согласованной BDSM/D/s-динамики. Создай открытый репозиторий и начни реализацию по приложенному техническому заданию. Нужен работающий код с проверками, а не только документация, набор интерфейсов или демонстрационные экраны.

## 1. Что заказчик действительно зафиксировал

- Приложение устанавливается самостоятельно. Один инстанс обслуживает одно закрытое пространство отношений.
- В пространстве может быть N доминантов и N подчинённых. Ограничения «ровно два пользователя» нет.
- Backend допустим на Python или Go. Клиенты: Telegram Mini App и нативное Android-приложение.
- Аутентификация участников через Telegram. Пользователи создаются исключительно оператором через консоль с указанием Telegram ID.
- Нужны правила, дневник, учёт наказаний, ритуалы, вознаграждения, в том числе вознаграждения за ритуалы.
- Нужны анкеты и опросы для участников и внешних людей без аккаунта приложения.
- Проект должен быть OSS. Начать нужно с создания репозитория и первой работающей реализации.

Не превращай эти требования в SaaS, публичную социальную сеть, маркетплейс или платформу с самостоятельной регистрацией.

## 2. Предлагаемые значения по умолчанию

Следующие решения выбраны для исполнимости задания, а не являются отдельно подтверждёнными пожеланиями заказчика:

| Решение | Значение для начала разработки |
|---|---|
| Рабочее название и slug | `Vowen`, `vowen` |
| Лицензия | `MIT`, полный стандартный текст без дополнительных ограничений |
| Backend | Python 3.13, FastAPI, SQLAlchemy 2.x async, Alembic, Pydantic 2 |
| База | PostgreSQL 17 |
| Telegram | aiogram 3, отдельный процесс бота с long polling |
| Web | Vue 3, TypeScript, Vite |
| Android | Kotlin, Jetpack Compose; нативный клиент, не WebView-обёртка |
| Развёртывание | Docker Compose, reverse proxy, HTTPS |
| Языки интерфейса | RU и EN; код и API-идентификаторы на английском |
| Первая поставка Android | APK для самостоятельной установки; публикация в магазине вне задания |

Название не проверено на домены, товарные знаки и занятость в магазинах. Не заявляй обратного. Отображаемое имя сделай настраиваемым. Не создавай одновременно Python- и Go-реализации. Версии Python/PostgreSQL выше являются целями совместимости, а не заявлением о самых новых версиях. Перед установкой выбери совместимые стабильные версии остальных зависимостей, зафиксируй lockfiles и запиши фактически выбранные версии.

## 3. Порядок чтения

1. `AGENTS.md`: обязательные инженерные правила.
2. `docs/PRODUCT_SPEC.md`: поведение продукта и границы MVP.
3. `docs/ARCHITECTURE.md`: модули, модель данных и API.
4. `docs/SECURITY.md`: аутентификация, гостевой доступ, приватность.
5. `docs/IMPLEMENTATION_PLAN.md`: порядок разработки и критерии приёмки.
6. `docs/REFERENCES.md`: первичные источники для технических ограничений.

Обозначения требований `REQ-*` стабильны. При изменении проекта сохраняй их трассировку до тестов и этапов.

## 4. Создание репозитория

Сначала проверь текущую директорию, Git-статус и доступные инструменты. Не перезаписывай существующий репозиторий и не удаляй чужие изменения.

Создай новый публичный OSS-репозиторий `vowen` в явно указанном workspace либо личном аккаунте, подтверждённом подключённым GitHub-инструментом. Не угадывай владельца по имени в переписке. Если имя занято, не изменяй существующий проект: создай безопасный новый локальный каталог и сообщи о конфликте. Для публикации используй доступный GitHub-коннектор либо настроенный GitHub CLI, если коннектора нет.

Публиковать разрешено только код, документацию и синтетические тестовые данные этого проекта. Перед первым push проверь staged-файлы и историю на секреты. Не публикуй Telegram ID реальных людей, токены бота, анкеты, дневники, дампы, переписку заказчика, адреса его серверов и пользовательские данные.

Если создание remote недоступно, создай локальный Git-репозиторий, продолжи разработку и явно укажи, что remote не создан. Не выдумывай URL. Не останавливай локальную разработку только из-за отсутствия сети или GitHub-полномочий.

Перенеси документы задания в репозиторий. Создай README на английском, `README.ru.md`, `LICENSE`, `CONTRIBUTING.md`, `SECURITY.md`, `CHANGELOG.md`, issue/PR templates, `.gitignore`, `.env.example` и CI. Для copyright используй подтверждённого владельца либо наименование `Vowen contributors`, не выдумывай юридическое имя человека. Security policy не должна предлагать публиковать реальные интимные данные или секреты в issue.

## 5. Что делать в первой рабочей сессии

Выполни M0 и начни M1 из плана. При достаточном рабочем контексте доведи M1 до критериев приёмки:

- воспроизводимый запуск и миграции;
- CLI-создание и блокировка пользователей;
- настоящая серверная проверка Telegram Mini App;
- Android-вход через подтверждение в боте;
- `/me`, сессии, отзыв доступа;
- контекстные отношения и запрет неразрешённых действий;
- минимальный работающий Mini App и собираемый Android-клиент;
- отрицательные тесты аутентификации и прав.

Анкеты и гостевой доступ реализуй следующим законченным этапом M2. Не размазывай работу по всем модулям, оставляя только заглушки. Нереализованные разделы не должны имитировать успешную работу.

## 6. Режим выполнения

Делай небольшие проверяемые изменения: тест → ожидаемое падение → реализация → успешная проверка → содержательный commit. Используй доступные инструменты и навыки разработки, но не требуй наличия конкретного коммерческого агента для сборки проекта.

Не задавай повторно вопросы, ответы на которые есть в документах. Неблокирующие инженерные решения принимай сам и записывай в ADR. Без согласования не меняй ограничения single-instance, CLI-only provisioning, Telegram-auth, нативный Android и отсутствие саморегистрации.

Не заявляй о прохождении тестов, которые не запускал. При отсутствии Android SDK, Telegram-токена или публичного HTTPS отделяй успешно выполненные локальные проверки от непроверенного живого сценария. Мок-тест не является проверкой интеграции с Telegram.

## 7. Финальный отчёт о выполненной сессии

Укажи реальный URL remote или путь локального репозитория; текущую ветку и commit; завершённые этапы; точные команды сборки и проверки с результатами; команды локального запуска; известные ограничения и следующий конкретный шаг. Не называй весь продукт готовым, если завершён только M0/M1.
