# Заявки на изменение ритуалов и правил

Заявку создаёт подчинённый в конкретных действующих отношениях. Профильная
метка роли не даёт полномочий. Решение принимает только доминант, назначивший
ритуал или правило, при действующих согласиях и соответствующем scope.
Другие доминанты и проверяющие отчёты эту заявку не видят и не решают.

`POST /api/v1/change-requests` принимает `kind`, `idempotency_key`, `reason`
и цель. Поддерживаются:

- `ritual_skip`: `assignment_id`, `occurrence_id`, версия выполнения
  `expected_version`. До одобрения выполнение не пропускается. Просроченный
  или уже изменённый слот нельзя пропустить по старой заявке.
- `ritual_pause`: `assignment_id`, версия назначения `expected_version`.
  Одобрение ставит назначение на паузу, отменяет ещё не выполненные слоты и
  подавляет связанные уведомления. Доминант возобновляет свою паузу; пропущенный
  интервал не восстанавливается. Для старых пауз без автора сохранено прежнее
  право возобновления получателем.
- `rule_add`: `relation_id` и `content` (название, описание, дисциплина).
- `rule_edit`: `assignment_id`, его `expected_version` и полный `content`.
- `rule_delete`: `assignment_id` и его `expected_version`. Одобрение отзывает
  только это назначение, сохраняя версии, историю дисциплины и назначения другим.

Одобрение добавления или изменения правила создаёт опубликованную версию и
назначение `pending_acceptance`. Подчинённый отдельно принимает точную версию;
старая активная версия действует до принятия замены. Изменение доминантом
текущей версии/черновика делает старое предложение неприменимым. Явные
управляющие сохраняются, но их полномочия проверяются заново.

`GET /api/v1/change-requests` возвращает доступные заявки и историю.
`POST /api/v1/change-requests/{id}/{approve|reject|withdraw}` принимает
`expected_version` заявки и необязательный `comment`. Подчинённый может отозвать
ожидающую заявку. После решения запись неизменяема; повтор того же решения
с тем же комментарием не применяет эффект повторно. Повтор создания с тем же
ключом возвращает ту же запись; изменение тела с прежним ключом даёт 409.

Заявка фиксирует версию соглашения, назначения и правила. Устаревшее одобрение
даёт 409; можно отклонить/отозвать заявку и отправить новую. Отзыв полномочий
закрывает доминанту чтение и принятие решений. Автор сохраняет собственную
историю. Причина, содержание, название цели и комментарий зашифрованы в БД;
записи заявки и её эффект записываются в одной транзакции. Уникальные индексы
и блокировки защищают от повторов и конкурирующих решений.

Это плановые изменения. Личная пауза, отзыв согласия и отказ от ещё не принятого
правила остаются немедленными. Прямой API пропуска и прямой плановой паузы
ритуала для подчинённого возвращает `REQUEST_APPROVAL_REQUIRED`.

Схема: Alembic `0020`, после `0019`. Откат удаляет историю заявок — перед откатом
нужна резервная копия. Локальная demo-база обновлена с сохранением данных.
Очередь заявок доступна в разделах ритуалов и правил; веб обновляет её при
возврате в раздел/приложение. Отдельная доставка этих заявок через Telegram
не добавлена. Android использует те же API и DTO; сборка и проверка на устройстве
отложены по указанию владельца.

Обновление 2026-10-18: по решению владельца прикладные payload больше не шифруются (0035). Упоминания зашифрованного хранения выше описывают прежнюю реализацию. Права доступа/приватность API сохранены; см. ../operations/plain-payloads.md.
