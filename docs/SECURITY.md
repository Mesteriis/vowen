# Безопасность и границы доверия

Требования этого документа обязательны начиная с этапа, который вводит соответствующую поверхность атаки. Это техническая модель, а не заявление о прохождении аудита, сертификации или соблюдении законодательства во всех юрисдикциях.

## 1. Модель угроз и честные ограничения

**REQ-23.** Защищаемся от постороннего посетителя, другого участника без прав, пересланной ссылки, подмены Telegram ID, повторного использования доказательства входа, случайной утечки в логах, конкурентных запросов и кражи backup без ключа.

Self-hosted оператор с root-доступом, кодом процесса и ключами может получить доступ к данным. Прикладной ACL не мешает ему читать БД или менять программу. Серверное шифрование не является E2EE. В UI и документации не обещать «даже администратор не прочитает». Защита от владельца сервера потребовала бы другой архитектуры и отдельной модели ключей.

Не обещать анонимность гостю с персональной ссылкой или аккаунтом Telegram. Не обещать техническое подтверждение возраста по checkbox. Отправленные Telegram-сообщения, скриншоты и экспортированные копии нельзя надёжно отозвать из чужого владения.

## 2. Telegram Mini App

**REQ-24.** Endpoint получает исходную строку `Telegram.WebApp.initData`. Backend проверяет её по официальной процедуре Telegram [R1]. Не доверять `initDataUnsafe`, переданному отдельно `user_id`, имени пользователя, данным из Android intent или одному наличию ID в локальной БД.

Требования проверки:

1. Ограничить размер строки, корректно разобрать query-string и отвергнуть повторяющиеся ключи.
2. Проверить HMAC-SHA-256 по алгоритму Mini App с токеном именно этого инстанса. Не смешивать его с Login Widget или OIDC. При построении data-check-string не переупаковывать JSON `user` и не терять подписанные поля.
3. Сравнивать подпись в constant time. Проверить наличие и тип `auth_date`, `user.id`, запретить `is_bot=true`.
4. Проектный максимум возраста `auth_date`: 300 секунд; допустимое отклонение в будущее: 30 секунд. Это настройки приложения, не заявленные лимиты Telegram.
5. После успешной криптографической проверки найти активного `users` по Telegram ID. Не создавать запись при отсутствии.
6. Ограничить повторный выпуск сессий по одному Telegram-доказательству. Ключ использованной assertion строить из проверенной подписи и контекста бота, не из сырой строки с переставляемыми параметрами. Одно доказательство выпускает не больше одной session family. Повтор после потери ответа требует переоткрытия Mini App, а не отключения replay-check.

Открытие приложения через профиль/menu button и особенности валидного `initData` необходимо проверить с реальным Telegram. Тестовый генератор подписи использует только синтетический токен и не попадает в production endpoints.

## 3. Android: подтверждение входа через бота

**REQ-25.** Для MVP выбран собственный challenge-flow, использующий официальные bot deep links [R2]. Это не называется OAuth/OIDC и не зависит от предположения о поддержке Telegram OIDC конкретной библиотекой.

### Протокол

1. Android генерирует случайный `client_nonce` из 32 байт и отправляет `POST /auth/android/challenges` с nonce и локальным названием устройства. Название считается непроверенным пользовательским текстом.
2. Backend создаёт `challenge_id` UUID, независимые случайные `start_token` и `poll_secret` по 32 байта, шестизначный display-код и срок 300 секунд. Сохраняются только хэши секретов и nonce. Display-код нужен для сравнения экранов, не является bearer-секретом.
3. Клиент получает challenge ID, `poll_secret`, display-код, срок и ссылку бота `https://t.me/<bot>?start=login_<start_token>`. Base64url без padding даёт 43 символа для 32 байт; с префиксом `login_` получается 49 символов, меньше Telegram-лимита 64 [R2].
4. Бот принимает start payload только в личном чате. Проверяет отправителя по полученному от Telegram `from.id`, локальному allowlist и свежести challenge. Показывает инстанс, устройство, тот же display-код и кнопки «Подтвердить вход» / «Отклонить». Сам `/start` вход не подтверждает.
5. Одобрение принимается только от того же Telegram-пользователя, которому показано подтверждение, после проверки callback и состояния. Неизвестный/отключённый пользователь не получает доступ. Пересланная кнопка не меняет подтверждающего.
6. Android проверяет статус через POST с `poll_secret` и `client_nonce` в теле, не в URL. После одобрения отправляет их в `/consume`. Секрет старта бота не подходит для poll или consume.
7. Consume атомарен: проверка срока, пользователя, nonce, секрета и состояния плюс создание session family выполняются в одной транзакции. Второй consume не выпускает токены. Rejected/expired/cancelled challenge никогда не превращается в сессию.

Не передавать access/refresh token в Telegram deep link или custom URL scheme. Возврат в Android может просто открывать приложение; само приложение получает результат из backend по доказательству владения своей ожидающей сессией.

Предупреждение на экране бота: подтверждать только собственный инициированный вход и совпадающий код. Нельзя обещать, что такой flow исключает фишинг при сознательном подтверждении чужой ссылки. Публичное создание challenge ограничить rate limit и TTL-очисткой.

## 4. Сессии и устройства

Для single-instance выбрать opaque tokens с серверной проверкой, а не обязательный JWT. Каждый токен имеет 32 случайных байта; в БД хранить SHA-256-хэш. У случайного высокоэнтропийного токена иной профиль, чем у человеческого пароля; не заменять его коротким PIN.

Проектные defaults: access TTL 15 минут; Android refresh family TTL 30 дней; Mini App refresh family TTL 12 часов. Refresh ротируется атомарно. Использование уже потраченного refresh отзывает его family. Клиенты сериализуют refresh-запросы, чтобы не создавать гонки собственными параллельными запросами. Потеря ответа refresh приводит к повторному входу, а не к бесконечной терпимости к повторному токену.

При каждом защищённом запросе проверять токен, session family и `users.is_active`. Отключение пользователя/отзыв сессии запрещают новые запросы после commit блокировки, не только после истечения access TTL. Уже начавшуюся сетевую передачу нельзя «отменить задним числом».

Выбранный MVP-транспорт для Mini App: access и refresh только в оперативной памяти текущего JS-контекста, bearer в Authorization. Не хранить их в localStorage, sessionStorage, IndexedDB, Telegram CloudStorage или URL. Закрытие/перезагрузка контекста требует повторной проверки Telegram. Это сознательный компромисс: нет зависимости от third-party cookies, но JavaScript/XSS остаётся угрозой, поэтому нужны строгая CSP и безопасный рендеринг. Не представлять in-memory хранение как защиту от уже исполняющегося вредоносного JS. Рекомендации по жизненному циклу session tokens см. [R5].

Android: access в памяти; refresh шифруется AES-GCM с ключом Android Keystore. Keystore хранит криптографический ключ, а не произвольную строку refresh token [R6]. Encrypted blob находится во внутреннем хранилище и исключается из backup. При logout, удалении аккаунта или смене инстанса удалить blob и относящийся к нему локальный контекст. PIN/биометрический app lock можно добавить позже, но он не заменяет серверный отзыв.

Не хранить полный Android device fingerprint. Список сессий показывает только собственные устройства, время и статус. Не писать чувствительные ответы в logcat, crash reports и HTTP-debug interceptor release-сборки.

## 5. Гостевые приглашения и опросы

**REQ-26.** Разные типы секрета имеют разные назначения и таблицы. Invitation token нельзя принять как member access token или Android poll secret.

### Ссылка и активация

- Сгенерировать 32 случайных байта, хранить хэш. Default TTL приглашения: 7 дней; оператор может сократить/изменить до выпуска.
- Формат ссылки: `https://host/f/<public_id>#token=<secret>`. Fragment снижает попадание секрета в HTTP access log, но сама ссылка остаётся чувствительной и может быть скопирована или сохранена браузером.
- GET/HEAD страницы и link preview не расходуют приглашение. Не включать в preview название формы, участника и другую чувствительную информацию.
- После явного нажатия «Открыть анкету» JS делает POST `/guest/invitations/exchange`. Сервер атомарно активирует приглашение и выпускает отдельную guest session; из адресной строки fragment удаляется через `history.replaceState`.
- Guest session привязана к одному приглашению и существует не дольше 24 часов или остатка TTL приглашения. Cookie `__Host-vowen_guest`: Secure, HttpOnly, Path=/, без Domain, SameSite=Lax. Cookie-подход здесь относится к гостевой top-level странице, а не к Mini App.
- Все изменяющие guest-запросы проверяют Origin и synchronizer CSRF token. `Referrer-Policy: no-referrer`, `Cache-Control: no-store`, запрет индексации, отсутствие сторонних скриптов и трекеров.
- Повтор exchange тем же действующим guest-сеансом не сбрасывает черновик. После активации один только исходный invite token не открывает черновик на другом устройстве. Для потери cookie нет восстановления по имени/Telegram ID: отправитель отзывает приглашение и создаёт новое, старый черновик закрывается.

Capability по ссылке не доказывает личность человека: первым активировать её может любой обладатель. UI не должен называть указанный отправителем адресат «проверенной личностью». Для внутреннего приглашения применяется проверка `recipient_user_id`, не этот гостевой режим.

### Отправка и квитанция

Один приглашённый ответ может быть финализирован только один раз. Проверить status/expiry/revocation непосредственно в транзакции финализации. Идемпотентный повтор того же submit возвращает то же submission, а не новую запись.

После отправки разрешить чтение/удаление своего ответа в текущей guest session и выдачу независимой квитанции с receipt-secret. Она открывает только управление этим ответом через `/guest/receipts/exchange`, не редактирование анкеты и не внутреннее приложение. Receipt-сеанс имеет только scopes `submission.read` и `submission.delete`; в отличие от сеанса заполнения он не получает `draft.write`/`form.submit` и может действовать после истечения исходного приглашения до срока хранения ответа. Receipt-secret хранить только хэшированным; срок не больше срока хранения ответа. Выдача новой квитанции отзывает прежнюю. Если ответ на запрос потерян, действующая guest session может перевыпустить квитанцию; сервер не обязан восстанавливать plaintext старого секрета.

Удаление тела ответа помечает submission `withdrawn`, удаляет ciphertext/файлы и отзывает reader-доступ. Проверять удаление в экспортных артефактах и незавершённых задачах. Остаточная техническая запись не содержит ответов. Данные в offline backup исчезнут по retention-политике; не обещать мгновенное исчезновение из всех резервных копий.

Читатели формы не видят черновики. Изменение `form_id`, `version_id`, `recipient_user_id`, submission ID и audience в запросе не позволяет выйти за capability. Связь гостя с будущим аккаунтом не выполнять автоматически.

## 6. Telegram-доставка и контакт без аккаунта

Бот не может произвольно начать личную переписку только по известному ID. Использовать существующий доступный чат или явно предоставленное право писать; официальный Telegram отдельно описывает ограничения начала разговора [R3].

`bot_contacts` не является allowlist и не предоставляет доступ к `/me`. Unknown `/start` без полезного контекста не создаёт пользователя. При действующем приглашении человек может разрешить уведомления и дать создать минимальную запись контакта. Сохранение Telegram-контакта не меняет идентичность уже отправленного bearer-ответа.

При отключённой доставке или блокировке бота результат приглашения: ссылка создана, автоматическая доставка не выполнена. Эти состояния раздельны. Не делать бесконечные попытки и не писать интимное содержимое в Telegram «для удобства».

## 7. Шифрование, хранение и удаление

**REQ-27.** Для чувствительных полей использовать стандартную библиотеку `cryptography` и AEAD AES-256-GCM, без собственной криптосхемы. При каждом шифровании новый nonce; повтор nonce с тем же ключом запрещён документацией библиотеки [R8].

Формат encrypted envelope: `key_id`, `nonce`, `ciphertext` с authentication tag, версия формата. AAD связывает payload с типом записи, её UUID и версией схемы. Подмена ciphertext между разными строками должна приводить к ошибке проверки, а не выдаче чужого текста.

Ключи хранятся отдельно от БД и Git в keyring-файле с ограниченными правами. Для MVP достаточно поддержанного keyring с активным ключом для новых записей и старыми ключами для чтения. Ротация выполняется пакетно с возможностью продолжения; старый ключ удаляется только после проверенного перешифрования и учёта backup. Потеря всех нужных ключей означает потерю доступа к ciphertext.

Обязательный шифруемый минимум: тела дневника, ответы и черновики форм, личные комментарии, тексты соглашений и дисциплинарных записей. Чувствительные описания правил, ритуалов и наград также хранить в encrypted payload. Служебные статусы, FK, расписания, Telegram ID и структурная схема анкеты могут оставаться видимыми в БД. Этот остаточный объём метаданных явно описать, не заявлять «зашифровано абсолютно всё».

До начала сбора гостевых ответов отправитель задаёт срок хранения; default 90 дней после отправки. Неотправленные черновики удаляются после истечения приглашения. Сроки 7 дней, 24 часа и 90 дней являются defaults проекта, не нормами закона. Внутренние дневники хранятся до удаления автором. Сводки и экспорт не должны бессрочно переживать исходные данные.

## 8. API, web и эксплуатация

Rate limits на auth, создание challenge, guest exchange, submit и bot callbacks; ограничения размеров схем/ответов и количества вопросов. Начальные пределы проекта: 100 вопросов, 100 вариантов одного вопроса, 10 000 символов свободного ответа, 512 KiB JSON-запроса; oversize возвращает понятную ошибку. Разрешать расширение через конфигурацию в разумных пределах, не обходя защиту worker и БД.

Для MVP пользовательский текст отображается как текст, HTML не поддерживается. DSL условий формы имеет allowlist операций, лимит вложенности и запрет `eval`. Вложения не включать, пока не реализованы ACL, content-type validation, ограничения размера, безопасные имена, выдача без исполнения и удаление.

Не логировать Authorization/Cookie, Telegram bot token в URL API-клиента, `initData`, guest fragments, poll secrets, request bodies и plaintext encrypted-полей. Pydantic validation errors должны быть очищены от исходных чувствительных значений. SQLAlchemy `echo=False` в production. Request ID случайный, без Telegram ID и названия формы.

Защита распространяется на reverse proxy, tracing, crash reports, CI-артефакты и резервные копии. Audit фиксирует действие, IDs и состояние, но не полные тексты. Администратор получает технический журнал, не отдельный UI «читать все дневники».

При восстановлении backup оператор проверяет ключи, права файлов, адрес инстанса и отключение реальной доставки в тестовой копии. Восстановление может вернуть записи, удалённые после даты backup: runbook обязан описывать применение актуальной политики удаления перед повторным открытием инстанса.

## 9. Обязательные отрицательные тесты

Поддельный/stale/future `initData`; дубликаты query keys; повтор Telegram assertion; неизвестный и заблокированный ID; stolen start token без poll secret; подтверждение другим Telegram-пользователем; двойной consume; refresh reuse; блокировка при ещё действующем access; нетранзитивные связи; отказ приватного дневника даже Dominant; доступ к чужому черновику; гостевой token на member endpoint; чужой invitation ID; одновременная отправка; revoke против submit; GET preview без расходования токена; повторный worker без двойной награды; plaintext-marker отсутствует в БД/логах; подмена AEAD payload; потеря/ротация ключа; удаление и восстановление backup.

## M4 implementation boundaries

Discipline proposals require direct current `discipline.propose` authority; only
named current reviewers can confirm completion. Recipient acceptance binds an exact
immutable version and cannot be performed by its author, reviewer or operator.
Recipients cannot rewrite assigned rule text or discipline conditions. Dispute and
withdrawal suspend execution, including during a personal pause. Content changes
require a new version and personal acceptance. See [transition matrix](M4.md).

Diary readership is independent of relationships. Entries default to private drafts;
published audiences are explicit reader lists or author-controlled member snapshots.
Future members are excluded until an explicit audience refresh. Lists, filters and
JSON exports apply the same ACL as detail reads; there are no cross-user totals or
plaintext text indexes. Entry deletion removes ciphertext and reader rows; edited
bodies and diary content are not copied into audit/outbox/notifications. This does
not remove backups or copies already obtained, and server key access is not E2EE.
