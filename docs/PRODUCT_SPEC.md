# Vowen: продуктовая спецификация

Статус: задание для начала реализации. Проектные решения по умолчанию отмечены в `START_HERE.md`; следующие разделы задают поведение будущего приложения, а не описывают уже существующий продукт.

## 1. Назначение и границы

**REQ-01.** Приложение помогает совершеннолетним участникам одной согласованной BDSM/D/s-динамики вести правила, ритуалы, дневник, дисциплинарные записи, вознаграждения и анкеты. Все данные хранятся в самостоятельно развёрнутом инстансе. Обязательное внешнее взаимодействие: Telegram для идентификации и доставки разрешённых уведомлений.

**REQ-02.** Одно пространство может включать произвольное число пользователей. На старте допустим один пользователь: он может войти и настроить свой профиль, но не может создавать отношения с самим собой. Нет таблицы организаций, выбора «пары», биллинга, публичного поиска людей, ленты или глобального рейтинга.

**REQ-03.** Пользователи появляются только после команды оператора с Telegram ID. Вход, `/start`, приглашение в анкету и заполнение анкеты не создают аккаунт. Нет скрытой регистрации через ORM `get_or_create`, импорт ответов, social login callback или Android onboarding.

**REQ-04.** Telegram Mini App и нативный Android используют один REST API. Внешняя форма открывается в обычном браузере без Telegram и без установки приложения. Android позволяет указать адрес собственного инстанса; центрального обязательного сервера нет.

## 2. Участники, отношения и полномочия

**REQ-05.** Отделить три понятия:

| Понятие | Назначение |
|---|---|
| Оператор инстанса | Развёртывание, секреты, CLI-пользователи, техническое обслуживание |
| Пользователь приложения | Аккаунт, сессии, профиль, личные данные |
| Контекстная D/s-связь | Согласованные полномочия одного пользователя относительно другого |

Профильные метки `dominant`, `submissive`, `switch` отражают самоописание, но не участвуют напрямую в разрешении запросов. A может быть Dominant относительно B и submissive относительно C. Направленные циклы допустимы, поскольку наследования прав нет.

Связь содержит `dominant_user_id`, `submissive_user_id`, версию соглашения, конкретный набор scopes и состояния `proposed`, `active`, `paused`, `revoked`. Одна активная версия связи на одну направленную пару. Нельзя создать связь с собой.

Начальные scopes: `rules.assign`, `rituals.assign`, `rituals.review`, `discipline.propose`, `discipline.review`, `rewards.grant`. Изменение доступов к дневнику и результатам анкеты не входит ни в один из них.

Связь активируется только после подтверждения обоими участниками точной версии соглашения и scopes. Расширение scopes требует нового подтверждения. Любой из участников может немедленно приостановить или отозвать связь. Возобновление требует подтверждения обоих. Оператор может предложить связь через CLI, но не имеет команды «согласиться за другого».

Наличие связи A → B не даёт A доступа ко всем объектам B: дополнительно нужны подходящий scope и включение в конкретное назначение/ACL. A → B и B → C не дают A → C. При нескольких Dominant правило «доступно всем доминантам» запрещено.

**REQ-06.** Глобальная пауза пользователя действует как дополнительный запрет на назначения и действия в отношении него. Снятие личной паузы не возобновляет связи, которые отдельно переведены в `paused`: для них сохраняется подтверждение обоих участников. Она не закрывает ему дневник, историю, настройки приватности, удаление своих доступных данных и выход из системы. Пауза не считается нарушением. Фоновый исполнитель повторно проверяет актуальную паузу перед новым действием. Уже отправленное сообщение отозвать гарантированно нельзя.

## 3. Соглашения и правила

**REQ-07.** Соглашение содержит версии текста, участников, ограничения, scopes и подтверждения. Подтверждение привязано к `agreement_version_id`, пользователю и времени. Редактирование опубликованной версии создаёт новую. Историческое подтверждение нельзя перенести на изменённый текст.

**REQ-08.** Правило содержит автора, название, описание, версию, назначенных адресатов и явно определённых управляющих. Шаблон правила и назначение пользователю являются разными сущностями.

Версия правила: `draft → published → archived`. Назначение: `pending_acceptance → active → paused/revoked`. Каждому адресату создаётся отдельное назначение и запись подтверждения. Отказ B не мешает C принять то же правило. Новая версия не активируется автоматически для прежних адресатов. Уже принятая версия остаётся действующей до замены или паузы; отзыв границ/полномочий применяется немедленно и имеет приоритет.

Доступны создание, просмотр, редактирование черновика, публикация, принятие/отклонение, пауза, архив и история. При частичном назначении нескольким людям API возвращает состояние каждого назначения; не скрывает ошибки за общим `success`.

Связь правила с возможным последствием справочная. Приложение не назначает и не увеличивает наказание автоматически за пропуск, отклонение или паузу.

## 4. Ритуалы и их выполнение

**REQ-09.** Разделить шаблон, версию, назначение, запланированное выполнение и отчёт пользователя:

`Ritual → RitualVersion → RitualAssignment → RitualOccurrence → RitualReport`.

Один шаблон можно назначить нескольким адресатам; расписание, отчёт, проверка и награда учитываются отдельно для каждого. Исполнитель видит свои назначения. Проверяющий видит только назначения, где он явно указан и имеет действующий scope относительно исполнителя.

MVP-расписания: разовое, ежедневно, выбранные дни недели. Время задаётся как локальное время и IANA timezone. События API хранятся в UTC. Правила переходов DST, восстановления пропущенных запусков и уникальности описаны в архитектуре.

Состояния occurrence: `scheduled`, `submitted`, `approved`, `needs_changes`, `missed`, `skipped`, `cancelled`. Отчёт подаёт только исполнитель. При `approval_required=false` подача приводит к `approved`; иначе требуется действие назначенного проверяющего. Для MVP достаточно одного из явно перечисленных проверяющих, схема кворума отложена.

`needs_changes` возвращает отчёт на доработку, сохраняя предыдущую попытку. Повтор HTTP-запроса не создаёт второй отчёт или вторую награду. Если два проверяющих одновременно принимают несовместимые решения, одно применяется, другое получает конфликт версий.

Пропущенное выполнение получает `missed`, но не создаёт дисциплинарную запись автоматически. Доступны календарь/список, напоминание, отметка выполнения, комментарий и фильтр по статусу. Вложения в отчёт входят в последующий этап, а не в начальный MVP.

## 5. Учёт наказаний / дисциплинарных действий

**REQ-10.** Пользовательская формулировка раздела: «Дисциплина» либо настраиваемое «Наказания». В API использовать `discipline`.

Запись содержит автора, одного адресата, возможную ссылку на версию правила и конкретное событие, описание, согласованные условия, срок, комментарии и историю статусов. Предполагаемое нарушение и согласованное последствие различать: сообщение автора не является автоматическим подтверждением факта другим участником.

Состояния: `proposed → accepted → in_progress → completed → confirmed`; дополнительные `disputed`, `declined`, `cancelled`. Принять/отклонить может адресат. Подтвердить завершение может только явно указанный проверяющий с актуальными полномочиями. Автор не завершает действие за адресата. Для нового адресата создаётся отдельная запись, не общий статус на группу.

При споре или отзыве согласия выполнение приостанавливается; нет автоматической эскалации. Смена описания после принятия требует новой версии и подтверждения. Видимость ограничена адресатом и явно назначенными сторонами. Автоматическая генерация инструкций для физических действий, оценка их безопасности и встроенный каталог подобных действий вне задания.

## 6. Вознаграждения

**REQ-11.** Есть каталог вознаграждений и отдельные выдачи конкретным участникам. Вознаграждение может существовать без ритуала и без баллов.

`RewardDefinition` содержит описание и условия. `RewardGrant` содержит получателя, выдавшего, источник, время и состояние: `offered`, `accepted`, `delivered`, `declined`, `cancelled`. История сохраняется. Отмена полученного не делается незаметным редактированием.

Автоматическая выдача за ритуал настраивается явно и ссылается на версию политики. Она запускается после `ritual.approved`, а не после произвольного нажатия кнопки. Одна occurrence и одна политика могут создать не больше одной выдачи данному получателю. Уже заработанное не списывается автоматически из-за паузы или изменения отношений.

MVP: ручная выдача, автоматическая выдача за одобренное выполнение, принятие/отклонение и отметка вручения. Баллы, магазин за баллы, серии и сложные условия отложены. Если баллы появятся, нужен неизменяемый ledger операций, а не редактируемый баланс как единственный источник истины.

## 7. Дневник

**REQ-12.** Запись принадлежит автору. Поля: дата, заголовок, текст, необязательное настроение, теги и видимость. По умолчанию `private`. Доступны `selected` с явным списком пользователей и `all_current_members` с зафиксированным списком текущих пользователей при публикации.

В snapshot включать только активных участников. Название последнего режима в UI должно пояснять, что будущие участники автоматически не добавляются. Для массового доступа использовать snapshot ACL, а не проверку «сейчас состоит в инстансе». Расширение аудитории выполняет только автор. Существующая D/s-связь не открывает дневник.

Редактировать и удалять может автор. Выбранные читатели не становятся редакторами. Черновики другим не видны. Отозванный читатель теряет будущий API-доступ, включая экспорт и историю, но приложение не обещает удалить уже сделанные скриншоты или сохранённые копии.

Поиск и фильтры учитывают ACL до выдачи результатов, счётчиков и подсказок. Не строить полнотекстовый открытый индекс приватных тел на этапе MVP. В audit не копировать текст и прошлые версии дневника. Вложения, комментарии читателей и расширенный редактор относятся к последующему этапу.

## 8. Анкеты и опросы

**REQ-13.** Один Forms Engine обслуживает анкеты и опросы. Анкета ориентирована на сбор структурированной информации, опрос может повторяться. Это тип/политика одного механизма, не две несовместимые модели.

### 8.1. Конструктор и версии

Форма: название, описание, автор, состояние `draft/published/archived`, версии схемы. У версии фиксированные ID вопросов, варианты с отдельными ID, обязательность, ограничения и условная видимость. После публикации схема неизменяема; исправление создаёт новую версию. Ответы и приглашения всегда ссылаются на конкретную версию.

MVP-вопросы: короткий текст, длинный текст, число, дата, boolean, одиночный выбор, множественный выбор, шкала, рейтинг, подтверждение ознакомления. Обязательность checkbox нельзя использовать для безусловного и неотзываемого согласия на будущие действия.

Следующий этап: матрица, ранжирование, файл/изображение и acknowledgement с отдельным представлением подписи. Нарисованная подпись или checkbox не объявляются квалифицированной электронной подписью.

Условная логика MVP: `equals`, `not_equals`, `contains`, `answered` и комбинации `all/any`; только ссылки на предыдущие вопросы, без циклов и исполнения кода. Скрытые вопросы не становятся обязательными. Сервер повторно вычисляет видимость, отбрасывает ответы на скрытые вопросы перед сохранением и не включает их в результаты.

Конструктор должен иметь web-интерфейс создания, редактирования, предпросмотра и публикации. Один лишь JSON API не закрывает пользовательский сценарий. Нативный Android в M2 поддерживает заполнение; полноценный редактор форм в Android может быть отложен с явным указанием в матрице возможностей.

### 8.2. Приглашения

**REQ-14.** Внутреннее приглашение привязано к конкретному `user_id` и версии формы. Получатель проходит обычную Telegram-аутентификацию. Пересылка ссылки другому участнику не даёт права заполнить приглашение вместо адресата.

**REQ-15.** Внешнее приглашение даёт гостевую capability только на одну форму. Заполнение не требует Telegram и не создаёт `users`. Ссылка секретная, имеет срок, может быть отозвана, допускает одну итоговую отправку. Повторный опрос создаёт новую волну и приглашение, не перезаписывает ответ.

До начала гостю показать, кто получит ответы, какие данные собираются, срок хранения и условия удаления. Предусмотреть самоподтверждение совершеннолетия без сбора паспорта. Не представлять его как доказанную проверку возраста.

Гость не видит участников, внутренние правила, другие формы, чужие ответы и служебную статистику. Гость не может изменять `respondent_user_id`, назначать себе role, менять список получателей результатов или выбирать другую версию формы.

### 8.3. Черновики, ответы и чтение

Состояния ответа: `draft`, `submitted`, `withdrawn`. Черновик сохраняется на сервере и виден только отвечающему. Создатель формы не читает чужой черновик. Итоговая отправка атомарна и идемпотентна. При отключении сети UI сохраняет видимый ввод до закрытия текущего окна и показывает, что сохранение не подтверждено; не пишет чувствительные ответы незаметно в browser localStorage.

Список читателей результата фиксируется в приглашении и показывается отвечающему. Автор шаблона не получает доступ автоматически, если он не включён в этот список. Удаление читателя уменьшает доступ. Расширение списка для уже собранного ответа требует нового явного разрешения отвечающего; в MVP вместо такого расширения использовать новое приглашение.

Внутренний пользователь видит свои отправленные ответы. Гость получает ограниченную квитанцию/средство управления собственным ответом. Удаление тела ответа не должно обходиться через audit, outbox или выгрузку. Подробности гостевых токенов и удаления заданы в SECURITY.

Ответ гостя не связывается с новым аккаунтом автоматически по имени, указанному ID или Telegram-профилю. Перенос в будущий аккаунт отложен до отдельного явно согласованного механизма подтверждения личности и желания отвечающего.

### 8.4. Отправка и повторение

**REQ-16.** В UI разрешённый пользователь создаёт приглашение, выбирает участника либо внешний доступ и копирует ссылку. Оператор может выполнить те же операции через CLI. Telegram-доставка возможна при наличии доступного боту канала/разрешения; сам Telegram ID не гарантирует возможность отправки [R2, R3].

Хранить контакт бота отдельно от аккаунта приложения. При действующем гостевом приглашении человек может начать разговор с ботом и явно разрешить последующие уведомления, не становясь участником. Если доставить нельзя, показать `manual_delivery_required` и предложить скопировать уже созданную ссылку, а не утверждать, что сообщение отправлено.

Повторяющийся опрос создаёт новую `survey_wave` и новые приглашения по расписанию. Начальный M2 поддерживает ручную отправку; автоматическое повторение и опрос после ритуала входят в M5. Дубликат события не создаёт вторую волну/приглашение.

Настоящая анонимность не входит в MVP. Не называй ответ анонимным, если его можно связать с персональным приглашением, `user_id`, контактами или техническими метаданными. Возможный будущий режим «без имени в интерфейсе» должен честно называться обезличенным отображением, а не гарантированной анонимностью.

## 9. Уведомления и настройки

**REQ-17.** Уведомления внутри приложения и через Telegram: новое назначение, наступление ритуала, ожидание проверки, награда, приглашение и отправленный ответ. По умолчанию текст нейтральный: «У вас есть обновление в приложении». Не включать название наказания, текст дневника, вопросы или ответы.

Пользователь выбирает доступные каналы, язык и тихие часы. Системные события не отменяют личный отказ от уведомлений. Внешние гости получают только сообщения по своему приглашению и только по разрешённому каналу. При блокировке бота доставка отключается без бесконечных повторов.

## 10. Интерфейсы и приёмка продукта

**REQ-18.** Mini App: домашний экран, свои назначения, правила, ритуалы, дисциплина, награды, дневник, формы, отношения и настройки. На домашнем экране не должно быть данных всей группы по умолчанию. Основное действие зависит от полномочий в выбранной связи, а не от единственного переключателя «я доминант».

Android: выбор HTTPS-инстанса, вход, домашний экран и те же основные повседневные сценарии. При смене инстанса локальные сессии и кэши прежнего сервера удаляются. Нельзя отправлять токен старого сервера на новый адрес.

Гостевой web: объяснение доступа, форма, прогресс/черновик, проверка перед отправкой, квитанция и удаление. Нет навигации внутрь закрытого приложения. Интерфейс адаптивный, RU/EN, светлая/тёмная тема, без обязательных внешних шрифтов/аналитики.

Наглядный интеграционный сценарий: оператор создаёт D1, D2, S1, S2; согласованы D1 → S1 и D2 → S2. D1 не может назначать действия S2 или читать дневник S1 без отдельного доступа. S1 выполняет ритуал, D1 подтверждает, выдаётся одна награда. Гость заполняет приглашённую форму; число `users` не меняется.

## 11. Что сознательно не входит в первый MVP

Multi-tenancy, публичная регистрация, подписки, платежи, AI-анализ интимных данных, генерация наказаний, социальная сеть, E2EE, гарантированная анонимность, offline-first синхронизация, универсальный workflow-конструктор, исполнение произвольных выражений, рекламные SDK и обязательные облачные сервисы.

Баллы, расширенные типы вопросов, вложения, полноценный нативный конструктор форм и сложные расписания сохраняются в roadmap. Их отсутствие нельзя скрывать за кнопками, которые возвращают фиктивный успех.
