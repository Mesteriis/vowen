# M6 release artifacts and scheduled backups

This slice implements artifact generation and automatic backups. It does not close
independent security review, physical Android acceptance or all M6 fault-injection
and clean-install acceptance items.

## Reproducible public artifacts

`make release-images` and `make release-android` require a clean Git tree. They
build a fresh `git archive HEAD`, never the operator's workspace or `.env`.
Each output includes the full revision, source epoch, SHA256SUMS and a JSON manifest.
Source/static tarballs have normalized ordering, modes, owners and timestamps.
Images use digest-pinned Python/uv/Node/Caddy, frozen dependency locks and an exact,
dependency-free uv_build backend. Runtime installs are non-editable; uv rebuild
cache metadata and its RECORD entry are removed, leaving runtime package data intact. The release workflow uses pinned BuildKit 0.34.0.
OCI layer timestamps use SOURCE_DATE_EPOCH and rewrite-timestamp; provenance/SBOM
attestations are disabled for the digest comparison, not asserted as generated.

The release workflow builds each linux/amd64 OCI image twice without layer cache
and requires equal image digests. Android clean builds run release unit tests/lint
and compare two unsigned APK hashes. Release versionCode is the commit epoch in
minutes; versionName includes the source SHA, independent of clone depth. A mismatch fails the job. This proves repeat
build equality for that revision/toolchain, not universal cross-toolchain equality.
Artifact upload retention is 14 days; a release owner should save accepted artifacts
before that expires. No registry push, GitHub release publication or device install
is implicit. CI receives no signing or production secrets.

Local preparation:

```sh
# Requires Docker/buildx, Python 3.13; the same pinned builder as release CI:
docker buildx create --name vowen-release --driver docker-container \
  --driver-opt image=moby/buildkit:v0.34.0@sha256:b059f8d7226d0b326bc871af489a5dddf65e36af4d20d14251b072974d9ee87c --use
make release-images
# Java 17 and Android SDK platform/build-tools 36; Gradle wrapper/locks are committed:
export JAVA_HOME=/YOUR/JAVA17
export ANDROID_HOME=/YOUR/ANDROID_SDK
make release-android
```

Output: `artifacts/release/<commit>/images` and `/android`. OCI archives can be
loaded with `docker load -i vowen-backend.oci.tar` / `vowen-web.oci.tar`; the tags
are `vowen-backend:<first12-of-SHA>` and `vowen-web:<first12-of-SHA>`.
CI release Java is pinned to Temurin17.0.20.1+1; the local environment may differ. The unsigned APK is
not installable. Personal installation still needs a stable signing key. Keep a
private JKS/PKCS12 key and password file outside the checkout, mode0600 in a
mode0700 directory. Do not add them to CI or Git. Use:

```sh
python3 scripts/sign_apk.py --unsigned /PRIVATE/vowen-unsigned.apk \
  --output /PRIVATE/vowen.apk --keystore /PRIVATE/release.jks \
  --password-file /PRIVATE/password
```

The helper passes password-file references, verifies APK v2/v3 signing and emits
public certificate/hash metadata. It refuses permissive/symlink credential files
and output replacement. Preserve the same key for upgrades; losing it prevents
updates of the existing install. A personal self-signed release is not a store
publication or device acceptance. Debug builds use a different signing identity.

## Daily encrypted application backup

`deploy/backup/vowen-backup.{service,timer}` run on the PVE host, invoking the
root-owned `scripts/ops/backup.py` installed at `/usr/local/lib/vowen/backup.py`.
Install `capture_backup.py` at that path inside the application LXC. Restic and
Python3 must be installed on the host. The guest already has Docker/PostgreSQL.
Create a dedicated repository on the backup storage, outside the LXC disk. Create
an independent random repository password in a root-owned0600 file, copy it to a
separate private recovery location, initialize with `restic init` explicitly,
and fill `/etc/vowen/backup.env` from the example. Repository and configuration
parent directories must be private. Initialization is never automatic on failure.

Capture includes an online consistent PostgreSQL custom dump, deployed source,
configuration, original data keyring/bot token and revision/schema/hash manifest.
Application writers continue running: pg_dump uses its consistent transaction;
source/config hashes must match before/after capture. Hold
`/run/lock/vowen-backup.lock` exclusively for deployments/key rotation too, so a
migration cannot overlap a backup. No data migration or app restart is needed to
install this backup tooling. Files contain sensitive data even when DB fields are
encrypted; temporary staging is owner-only and removed on success and normal failure. Abrupt guest termination can leave
root-only staging in `/run` until reboot or operator cleanup. Guest
staging is in `/run` and limited by available RAM; oversized dumps fail without
pruning old backups. Use a separately protected larger staging area before growth
exceeds that capacity. No raw DB/configuration data is emitted to the journal.

Sequence: capture → restic encrypted snapshot → repository check → authenticated
restore and exact archive hash comparison → scoped retention/prune → check again.
Any failure before retention leaves existing snapshots intact. Retention failures
fail the service; they are not reported as successful backups. An exclusive lock
prevents overlap; no automatic stale-lock removal is performed.

Defaults: daily03:45 Europe/Madrid, randomized delay up to5minutes, persistent
catch-up after downtime; keep-last3 plus7daily/4weekly/6monthly snapshots (union of
calendar buckets with actual snapshots, not deletion after a fixed number of days).
Policy is limited to the exact instance hostname and vowen-app tag, grouped by
host/tags. It cannot prune another backup set. These are starter operator defaults.
See [restic retention semantics](https://restic.readthedocs.io/en/stable/060_forget.html).

```sh
systemctl daemon-reload
systemctl enable --now vowen-backup.timer
systemctl start vowen-backup.service
systemctl status vowen-backup.service vowen-backup.timer
journalctl -u vowen-backup.service --since today
```

The systemd service exits nonzero on capture, encryption, check, restore or prune
failure. Monitoring must alert on failed runs and stale latest snapshots; a timer
being active alone is not evidence of completed future backups.

## Off-host copy and recovery

`pull_backup.py` transfers only encrypted repository files over an already trusted
SSH alias, under the same host lock. It uses BatchMode/connection timeout, owner-only
staging, safe tar extraction, rejects links and checks the repository locally with
a separately stored password before replacing an atomic current-generation link.
Failed transfers/checks preserve the previous generation. An hourly user launchd
job can invoke it on macOS; sleeping/offline clients catch up when next run. This is
conditional off-host replication, not an always-on remote vault. The source retains
calendar history; the client mirrors a verified generation of that history.

```sh
python3 scripts/ops/pull_backup.py --ssh-host YOUR_PVE_ALIAS \
  --remote-repository /mnt/backup/vowen/999/restic \
  --destination /PRIVATE/vowen-repository --password-file /PRIVATE/restic-password
```

Recovery: set RESTIC_REPOSITORY/RESTIC_PASSWORD_FILE privately, inspect snapshots,
`restic dump SNAPSHOT snapshot.tar > /PRIVATE/snapshot.tar`, extract only in a0700
scratch directory, verify manifest hashes. Restore database.dump into a new database
with pg_restore and use the backed-up original keyring. Do not substitute a new key.
Wrong repository passwords must fail authenticated reads. Test data-key recovery
separately. Select the captured source/schema before starting a scratch instance.
Never restore over production without a fresh backup and reconciliation of later writes.

The root backup operator can read backed-up data keys. Encryption does not provide
privacy from that operator or from a compromised client holding the recovery key.
