# M4: discipline and diary

## Discipline

A record is an allegation and a voluntary proposal, not proof of a violation.
`POST /api/v1/discipline-records` requires current direct `discipline.propose`
authority over the one recipient. Every explicitly named reviewer needs current
`discipline.review` authority. Author, recipient and reviewer set are fixed for
that record. New participants require a separate record.

Content, deadline and optional exact rule-version / ritual-occurrence links live
in immutable encrypted versions. A rule link must refer to a version previously
accepted by this recipient and visible to the proposer. An occurrence must belong
to the recipient and be visible to the proposer. Linking either does not assert
that the recipient agrees a violation occurred. The rule title is snapshotted in
the encrypted version; the original rule version is never changed.

| Action | Actor | Source states | Result |
|---|---|---|---|
| accept | recipient | proposed | accepted |
| start | recipient | accepted | in_progress |
| complete | recipient | in_progress | completed |
| confirm | explicit reviewer with current scope | completed | confirmed |
| decline | recipient | proposed | declined |
| dispute | recipient | proposed, accepted, in_progress, completed | disputed |
| cancel | recipient or currently authorized author/reviewer | any nonterminal state | cancelled |

Positive transitions also require the proposer's current authority and unpaused,
active participants. Withdrawal, decline and dispute remain available to the
recipient during a pause or after authority is revoked. Revoked actors lose list,
detail and history access; the recipient retains their history. Disputed records
cannot continue. The author may submit a new immutable version requiring fresh
recipient acceptance; terminal records cannot be revised. The recipient and
reviewer cannot revise conditions or the linked rule. Rule templates remain
editable only by their author; assigned rule text is never recipient-editable.

Every mutation requires the current revision and, for transitions, exact content
version. PostgreSQL row locks serialize conflicting reviews and authority changes.
Creation uses an author-scoped idempotency key; retrying changed content is a
conflict. Each history entry records actor, time, status, revision and version;
comments are encrypted. No automatic escalation, generated physical-action
instructions, automatic violation finding or automatic discipline is implemented.

## Diary

`/api/v1/journal` supports create, list, detail and author-only editing;
`/{id}/delete` requires a revision and removes entry ciphertext and reader ACL.
`/export` returns only the caller's currently accessible entries. Search and tag
filters apply after ACL selection and before returning any result. There are no
cross-user totals, history endpoints or plaintext search indexes.

Entries default to **private drafts**. Only the author sees a draft regardless of
its intended audience. Published entries use private, selected readers, or a
snapshot of active, unpaused current members excluding the author. Editing an
existing all-current entry never adds new members; the author must explicitly
request `refresh_audience` or choose a new audience. Readers are never editors.
A relationship, profile label or operator context grants no diary access.
Paused/inactive authors or readers cannot share/read another participant's entry;
the author retains access to their own diary during a pause.

Date, title, body, mood and tags are encrypted in one record-bound envelope.
Editing replaces that envelope; old diary bodies are not retained in audit or
history. No diary content is placed in notification/outbox payloads. Clients render
plain text, never HTML. Reader revocation controls future server reads, not copies
already received. Server operators with key access are outside this protection;
this is not E2EE.

## Clients and verification

Mini App and native Compose Android provide creation, exact-version consent,
transitions, comments, version/history views, diary editing, audience selection,
filtering and confirmed deletion. Mini App additionally downloads the ACL-filtered
JSON export; native file export and rich diary attachments/comments are not part
of this slice. Forms/ritual evidence functionality is unchanged.

Migrations 0015 and 0016 extend schema 0014 without backfilling private content.
Run `make migrate-test` before tests and migrate the application database before
starting a newly built API/worker. Old and new API revisions must not share a
partially migrated runtime. Production deployment is a separate operational step.
