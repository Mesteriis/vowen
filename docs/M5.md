# M5: recurring surveys and personal notifications

## Survey plans and waves

`GET/POST /api/v1/survey-schedules` lists the member's authored/received plans or
creates a plan from an owned published form version. A plan fixes that version,
one internal recipient and an explicit reader snapshot. Its configuration is
immutable: create a new plan to change version, audience or trigger. The author
is not automatically a reader. Automatic guest subscriptions are not implemented;
create a fresh guest invitation manually using the existing member/guest flows.

Periodic plans use the existing once/daily/weekly IANA schedule, including selected
weekdays. The window is the invitation lifetime, 1–168 hours. Missing DST times
shift by the gap; repeated times produce one wave at the first occurrence. The
worker processes at most 31 local days per plan and 50 rotating plans per tick.
Old expired/before-creation/paused slots are recorded as skipped; they do not create
invitations or a backlog of obligations. Each `(plan,event)` is unique. Each new
wave creates a separate invitation, encrypted draft and submission; old answers
and their form versions remain unchanged.

Feedback plans bind a current ritual assignment, its revision and direct authority
revision. They create a wave after an approved occurrence, once per occurrence,
with no backfill of approvals predating the plan. The worker processes up to 100
unprocessed approvals per plan per tick. Assignment/authority changes require a
new plan after participants have agreed; restoring rights does not reactivate a
plan bound to the old revision. Current source authority is checked again before
sending its queued invitation notice. Existing response readership remains governed
by its independent form invitation/retention rules.

`POST /survey-schedules/{id}/pause|resume` changes only the caller's own pause with
optimistic revision checks. The author cannot remove the recipient's pause, nor
vice versa. Resuming does not recreate blocked historical slots. Pausing stops new
waves and queued survey invitation delivery; it does not erase existing answers
or silently revoke already issued invitations. Personal account pause also blocks
new waves. A paused/unavailable selected reader causes a skipped wave, never an
expanded audience. Archiving the pinned form version stops future waves.

The author can use `POST /survey-schedules/{id}/send-now` with an idempotency key
and expected revision for a fresh manual wave. Retries of the same key return the
same wave. `GET /survey-schedules/{id}/waves` exposes history only to author and
recipient; it does not grant either access to answers. Paused/unavailable sources
produce a skipped result. Clients retain mutation keys after failed requests.

## Personal notification settings

`GET/PATCH /api/v1/me/notifications` manages only the authenticated member's own
`in_app` and `telegram` channel choices, quiet interval and optimistic revision.
Defaults preserve existing channel availability; quiet hours start disabled with
22:00–08:00 prefilled. These are implementation defaults. The IANA timezone comes
from the profile. Quiet hours defer Telegram notices, without consuming attempts;
tasks, reviews, answers and history remain available. A DST fold is quiet through
the later end boundary; gap boundaries shift forward. Untouched delayed notices
are re-evaluated after settings change, preserving actual retry backoff.

Turning off in-app notices hides neutral ritual/reward feeds, not the underlying
records. Re-enabling may show existing history. Turning off Telegram cancels queued
messages and advances a generation fence, including transactions that commit after
the cancellation query. Off/on never revives cancelled deliveries. Both member and
form outboxes recheck active users, personal pause, channel, bot opt-in generation,
expiry and applicable audience/authority immediately before sending.

Selecting Telegram does not call `/notifications_on`, create a bot contact or
confirm consent. Each participant still opts in personally through the bot.
Blocked-bot responses disable that contact and advance its generation; recovery
requires personal opt-in. Notices remain neutral, without diary content, questions,
answers or discipline details. Requests already in flight cannot be recalled.
Member ritual/reward delivery retains its uncertain-send fencing; form delivery
retains its bounded at-least-once retry behavior, so ambiguous network failures may
duplicate a neutral form notice. Survey invitation/wave creation itself is unique.

## Client flows and limits

Mini App and native Android have plan creation, periodic/approved-ritual triggers,
explicit readers, individual pauses, manual new waves and history. Participants
fill the ordinary native/web form runner with server drafts, acknowledgement and
review before submission. Android also exposes invitation TTL/retention/delivery,
archive, invitation revocation and reader removal. No WebView is used.

Notification editors preserve input after network failure and refresh on confirmed
save. Conflicts require refreshing the current revision. A permanently revoked web
session unmounts private panels and explains reopening through the bot for a fresh
Telegram assertion. Replay protection is preserved. Android retains its serialized
refresh and instance-switch isolation. No offline-first synchronization is claimed.

RU/EN controls and device-local dark/light/system appearance are available in member
and guest web and Android entry. Appearance is a non-sensitive local device setting;
authentication tokens remain outside web storage. Velvet startup artwork remains tied
to real loading. Responsive layout and Mini App safe-area behavior are preserved.
The advanced Android condition editor/preview and Android diary file export remain
explicitly deferred; existing form conditions are preserved by the basic editor.

## Migration and release

0017 adds personal notification settings, outbox generation fences and form quiet
scheduling; 0018 adds plans/waves and their uniqueness/index. Stop writers, back up
DB plus keyring/config/source, restore/rehearse on a separate database, then migrate
before starting the new API/worker/poller. Old API schema 0016 and new API schema
0018 must not share running writers. New fields have backward-preserving defaults;
no relation scopes or participant consents are added by either migration.

Downgrade drops M5 settings/plans/waves and fences. After real M5 use it is destructive;
choose a data-preserving rollback/restore before downgrading. Local migration tests
use synthetic existing profile/form/encrypted-journal rows and prove preservation
through 0016 → 0018 and an empty-M5 downgrade. Production deployment and live
Telegram acceptance are separate from this implementation.
